# Git vs SVN

Краткое сравнение после статьи «Git vs SVN» и практики на занятии 2.

## 1. Почему в Git ветвление «дешёвое», а в SVN — «дорогое»?

В Git ветка — это указатель (ссылка) на коммит, а не копия файлов. Создание ветки почти ничего не стоит: Git записывает новое имя, которое смотрит на тот же снимок, что и текущий `HEAD`. Переключение и слияние тоже работают с графом коммитов, а не с копиями каталогов.

В SVN ветка исторически — копия директории в репозитории (обычно `branches/feature` как копия `trunk`). Даже с дешёвым копированием на сервере это тяжелее операционно: ветка живёт на центральном сервере, merge часто ручной, история слияний отслеживается хуже. Поэтому ветки в SVN заводят реже и «дороже» по времени команды.

## 2. Можно ли в SVN сделать коммит без интернета? Почему?

Нет, полноценный коммит в SVN без сети сделать нельзя. SVN — централизованная система: ревизия появляется только на сервере. Без доступа к нему можно править файлы локально, но нельзя зафиксировать ревизию, создать ветку «как в Git» и посмотреть полную историю.

В Git репозиторий полный у каждого: `git commit` пишется в локальную базу. Интернет нужен только чтобы обменяться коммитами (`push` / `pull` / `fetch`).

## 3. В каких сценариях SVN до сих пор может быть предпочтительнее Git?

- Крупные монорепозитории с огромными бинарными файлами, где нужен checkout одной папки, а не всего дерева.
- Legacy-контуры (госсектор, банки, 1С-окружения), где уже выстроены процессы, хуки и права вокруг SVN, и миграция дороже, чем поддержка.
- Жёсткая централизация: один сервер, простая модель прав «кто может писать в trunk», без распределённых копий исходников на каждой машине.

Для новых проектов это редкость: почти всегда выбирают Git. SVN полезно знать, чтобы сопровождать старые системы, а не чтобы стартовать на нём новый сервис.
